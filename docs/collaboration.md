# 내부 토론과 inbox

## 사용자 흐름

1. 같은 신원을 실행하는 외부 실행기를 중지하고 허브 자동 응답을 켭니다.
2. 채널을 선택하고 에이전트 멘션을 체크해 요청을 보냅니다. 설정된 에이전트 중 첫 요청에 멘션한 에이전트만 참여하며, 해당 참여자 전원의 승인으로 완료합니다.
3. 대화 탭에서 요청·에이전트 토론·최종 결과를 시간순 말풍선으로 확인합니다.
4. 진행 중 같은 채널의 새 멘션 요청은 추가 지침으로 반영합니다. 별개 작업은 다른 채널에서 시작하세요.
5. 동일 최종안에 전원 찬성이면 최종 결과 하나를 Coral에 전송합니다. 반대·실패·한도 초과 시 보류 사유를 전송합니다.

## 비동기 진행과 검증

- 모든 참여자가 같은 요청을 바탕으로 자신의 의견·근거·위험을 준비합니다. 다른 참여자의 의견과 질문은 전원 제출 전까지 전달하지 않습니다. 화면에는 제출 상태만 표시합니다.
- 전원 제출 후 작성자를 표시해 의견을 함께 공개합니다. 첫 제출자의 답을 자동으로 최종 후보로 채택하지 않습니다.
- 대표가 모든 주장을 비교하고 실제 쟁점만 질문합니다. 질문받은 참여자만 근거를 답변합니다. 억지 반대는 요구하지 않습니다.
- 조율 담당자가 전체 의견과 남은 이견을 바탕으로 통합안을 작성한 후 전원이 동일 해시의 통합안을 검증합니다. 3인 팀 기본 호출은 독립 의견 3 + 쟁점 확인 1 + 통합 1 + 검증 3 = 8회입니다. 질문·수정·형식 복구는 추가 호출을 사용할 수 있습니다.
- 구체적인 `messages` 질문은 수신자의 예정 과제에 우선 묶습니다. 예정 과제가 없거나 `urgent: true`인 질문은 별도 inbox 확인 작업을 예약합니다. 실행 중 입력은 바꾸지 않고 다음 호출에서 처리합니다. 같은 수신자의 미실행 질문 작업은 합칩니다.
- 추가 질문과 조사 결과가 후보 작성 후 도착하면 기존 승인만으로 제출하지 않고 최신 근거를 반영한 수정안을 다시 검토합니다. 미완료 작업이 남아 있으면 최종 제출하지 않습니다.
- 전원 명시적 APPROVE가 있어야 최종 제출합니다. 반대는 담당자별 조사 → 수정안 → 전원 재검토로 이어집니다. 질문이나 단순 답글은 승인이 아닙니다.

참고 프로젝트의 독립 실행·inbox·승인 원칙을 적용한 방식입니다. 그 프로젝트의 API 백엔드나 상주 모델 세션을 이식한 것은 아닙니다. 구독 CLI는 여전히 호출마다 실행되며 생성 중 토큰 스트리밍도 제공하지 않습니다. 속도는 CLI 시작 시간과 각 모델 응답 시간의 영향을 받습니다.

진행 중 추가 지침이 들어오면 그 지침을 보지 못한 후보는 합의 처리하지 않습니다. 모델이 거짓 근거나 잘못된 판단을 제시할 가능성 자체는 없앨 수 없으며, 전원 찬성이 객관적 최적성의 증명은 아닙니다.

## inbox와 저장

선택한 데이터 폴더의 `database/queue.sqlite3`에 있는 `collab_*` 테이블에 요청·단계·과제·토론·쟁점·수신함을 저장합니다. 공유 결과는 모든 참여자의 inbox로, 구체적인 질문은 수신자의 inbox로 전달합니다. 각 CLI 호출 시작 시 수신함을 읽고 그 입력을 과제에 저장합니다. 기본 모드에서는 실행 중인 CLI에 메시지를 주입하지 않습니다. 아래 Claude 실험 옵션을 켠 경우에만 읽기 도구 완료 경계에서 추가 수신합니다.

내부 토론은 모델이 공개한 분석 결과·근거·질문입니다. 비공개 추론 스트림을 수집하는 기능이 아닙니다. 미열람 메시지와 사용자 추가 지침은 내용 전체를 전달합니다. 이미 읽은 이력만 최근 24건·각 1800자로 제한합니다. 요청과 동일한 현재 후보안의 중복 본문은 inbox에서 제외하고 별도 필드로 전달합니다. 역할과 쟁점도 유지합니다. 이전 이력의 긴 근거는 제한으로 생략될 수 있으며, 미열람 내용이 많으면 입력량이 커질 수 있습니다.

Coral은 사용자 요청과 최종 결과의 통로이며 내부 토론의 단일 기록 원본은 허브 DB입니다. 다른 기기와 내부 inbox를 동기화하는 기능은 없습니다.

## 한도와 복구

- 요청별 최종안 최대 3개, CLI 최대 30회, 총 45분; CLI 한 번은 최대 10분.
- 한 명이라도 독립 의견 제출에 실패하면 공개·토론을 시작하지 않고 보류합니다. 합의에 이르지 못하면 미확정 통합안과 남은 이견을 최종 보류 기록에 남깁니다.
- 진행 과제는 실행기 재시작 후 자동 재실행하지 않고 보류합니다. 미실행 과제는 DB에 보존합니다.
- 중지·설정 변경·채널 닫기는 해당 협업을 취소하며 늦게 끝난 결과는 합의에 반영하지 않습니다.
- 최종 결과를 DB에 먼저 저장하고 Coral 응답 표식으로 재전송을 조정합니다. 분산 트랜잭션이 아니므로 정확히 한 번 전달을 절대 보장하지 않습니다.
- 첫 연결·관찰 모드 기간의 과거 요청은 실행하지 않습니다.
- 같은 신원의 외부 실행기와 동시에 사용하지 마세요.

## 검증

`python -m unittest discover -s tests -v`는 스크립트형 작업자로 기본 8회 독립 의견·선택적 토론 흐름과 전원 제출 전 비공개 처리, inbox, 역할 분담, 반대→담당 조사→수정→재승인, 한도, 재시작, 중복 전송, 뒤늦은 사용자 지침을 검증합니다. 실제 CLI 검증은 구독 사용량을 소비하므로 별도로 수행합니다.

### Plan response format recovery

Each phase receives an explicit JSON output shape. If plan assignments are missing or invalid, the host retains the response and requests one correction. A second invalid response blocks the round with a format error, rather than suggesting disagreement. Correction calls count toward the execution budget. Votes and proposal hashes are never fabricated.

참여 팀은 요청 시작 시 확정됩니다. 진행 중 추가 메시지의 멘션은 팀을 늘리거나 줄이지 않으며 추가 지침으로 처리합니다. 다른 참여 조합의 별개 작업은 다른 채널에서 시작하세요.

### 호출 절감 1단계 (2026-09-16)

- `messages`의 `kind`는 기본 `question`; `notice`는 정보 공유이며 별도 수신 응답 호출을 만들지 않습니다. 새 정보에 따른 후보안 재검토는 여전히 필요할 수 있습니다.
- 일반 질문은 같은 요청·수신자의 미실행 과제에 함께 전달합니다. 예약 이후 다른 과제가 생긴 경우에도 실행 직전에 합칩니다. 실행 중 과제의 입력은 변경하지 않습니다.
- `urgent: true` 질문은 별도 consult 예약을 유지하되 실행 중인 CLI를 중단하지 않습니다. 같은 대기 질문의 긴급 전환도 지원합니다.
- 같은 발신자·수신자·종류·본문의 미처리/처리 중 메시지는 중복 등록하지 않습니다. 처리가 끝난 뒤 다시 묻는 것은 허용합니다.
- 질문 답변은 일반 과제에 묶여 처리되더라도 새 근거로 반영하여 오래된 후보안의 승인만으로 최종 제출하지 않게 합니다.
- 원래 요청을 프롬프트에 두 번 넣지 않습니다. 과거 문맥을 무조건 제거하거나 모델 요약 호출을 추가하지 않습니다.
- 이는 호출 경계에서 묶어 전달하는 최적화입니다. 실행 중 도구 결과에 삽입하는 0-turn 어댑터나 drift-guard 패키지 연동은 아닙니다.

검증: 모의 3인 흐름에서 기본 8회, 별도 질문 하나가 필요한 경로는 9회 실행으로 전원 승인에 도달합니다. 실제 구독 CLI 토큰 절감률이나 답변 정확도 향상률을 측정한 결과는 아닙니다.

### 도구 완료 경계 수신: Claude 실험 어댑터 (2026-09-16)

연결 및 에이전트 설정의 **Claude 도구 완료 시 메시지 수신** 옵션으로 활성화합니다 (`zero_turn_agents: ["claude"]`). 새 설치 기본값은 꺼짐입니다. 전역 Claude 설정을 수정하지 않고 각 HUB 작업의 `--settings` 파일에 명령형 `PostToolUse` 훅만 추가합니다.

- 현재 지원: Claude의 Read/Glob/Grep 완료 경계. 훅은 DB 버퍼를 읽을 뿐 모델을 호출하거나 Stop/재프롬프트를 사용하지 않습니다. 모델이 도구를 사용하지 않으면 다음 과제 전달을 유지합니다.
- 독립 의견 준비 단계에서는 도구 경계 수신도 비활성화합니다. 이후 단계부터 적용합니다.
- 대상: 실행 중인 동일 요청·수신자의 미열람 question/notice/guidance. 동시에 여러 도구가 끝나도 같은 이벤트는 한 번만 제시합니다.
- 훅이 제시한 기록만으로 읽음 처리하지 않습니다. 해당 CLI의 최종 JSON `received_event_ids`와 실제 훅 제시 기록이 일치할 때만 수신을 확인합니다. 수신 확인은 의미상 정답·충분한 검증을 보장하지 않습니다.
- 확인된 질문의 불필요한 일반 consult 예약만 취소합니다. 명시적인 urgent 요청은 유지합니다. 수신 확인이 없거나 훅이 실패하면 메시지는 미열람으로 남아 다음 과제로 전달됩니다.
- 한 훅은 최대 8건·본문 묶음 약 6,000자 범위입니다. 큰 메시지와 초과분은 버리지 않으며 다음 도구 완료 또는 다음 과제로 전달합니다. 취소·종료된 작업에는 주입하지 않습니다.
- 새 근거가 들어오면 기존 승인 상태를 그대로 최종 합의로 처리하지 않습니다. 늦게 받은 근거는 보수적으로 후보 재작성·재검토를 유발할 수 있으므로 항상 전체 호출 수가 줄어드는 것은 아닙니다.
- 별도 수신 호출을 추가하지 않는다는 의미의 0-turn입니다. 메시지 본문 입력 토큰과 원래 도구 수행 후 추론 비용은 발생합니다. drift-guard의 버퍼·안전 경계 원칙을 적용한 HUB 어댑터이며 외부 패키지 자체를 설치한 것은 아닙니다.

확인: Claude Code 2.1.159에서 HUB 어댑터의 한 번의 CLI 실행 중 도착한 테스트 메시지를 PostToolUse로 제시 → 최종 답변의 표식·이벤트 ID 확인 → 예약된 일반 consult 취소까지 실제 검증했습니다. 테스트 메시지는 로컬 격리 DB에서만 사용했습니다.

Codex 0.154.0은 공식 문서상 PostToolUse와 additionalContext가 있으나 비관리 훅의 신뢰 등록이 필요합니다. 이 구현은 신뢰 우회 플래그나 전역 설정 변경을 사용하지 않으며 Codex는 1단계 방식으로 유지합니다. Cursor는 설치된 CLI에서 실제 수신이 확인된 뒤에만 어댑터를 활성화할 예정입니다.

공식 근거: [Claude hooks](https://code.claude.com/docs/en/hooks#posttooluse), [Codex hooks와 신뢰](https://developers.openai.com/codex/hooks), [Cursor hooks](https://cursor.com/docs/hooks).

Cursor 추가 검증 (2026-09-16): CLI 2026.09.10-fd3934a, 실행 상한 300초. 정상 종료까지 56.16초, 첫 출력 34.12초, CLI 보고 API 처리 21.411초. 격리 프로젝트의 sessionStart/preToolUse/postToolUse 명령 훅 호출 기록과 추가 문맥 수신은 확인되지 않았습니다. 이 결과는 해당 설정 경로에서의 미확인이며 Cursor 전체의 훅 미지원이나 타임아웃으로 판정하지 않습니다. CLI 시작 전후의 시간은 준비·연결 등 여러 요인을 포함할 수 있습니다.


### 요청별 실행 기록

최종 결과·보류·취소 메시지 아래의 실행 기록에서 요청 경과 시간, 에이전트별 CLI 실행 횟수·시간, 질문 묶음 전달, 도구 경계 제시·수신 확인, 그 수신으로 취소한 일반 consult 수를 확인합니다. 취소 건수는 처리 코드의 실제 취소 사유로 집계하며 토큰 절감량으로 환산하지 않습니다. 묶음 전달은 일반 과제에 전달한 질문–수신자 쌍이며 처리 성공을 뜻하지 않습니다. 경계 수신과 중복 집계하지 않습니다.

새 실행은 프로세스 시작부터 종료까지 runs/<task>/metrics-<invocation>.json에 기록합니다. 재시도는 별도 실행이며 CLI 시작 자체가 실패하면 실행 횟수에 포함하지 않습니다. 도입 전 작업은 DB 실행 기록 기반으로 표시하며 재시도 시간이나 토큰이 누락될 수 있습니다. 전체 시간은 요청부터 종료까지이고 에이전트 시간은 각 실행 시간의 합이므로 병렬 실행 시 합계가 다릅니다.

토큰은 native CLI의 result.usage 또는 Codex turn.completed.usage에 있는 정수 필드만 수집합니다. 모델 답변에 적힌 자체 추정치는 수집하지 않습니다. 입력·출력·캐시 필드는 구분하며, 확인한 호출 수/전체 호출 수를 표시합니다. 미제공은 확인 불가이며 금액·절감률을 추정하지 않습니다. 이전 실행 로그를 소급 분석하지 않습니다.


### Codex 도구 완료 경계 수신 (실험적)

Codex도 선택형 `zero_turn_agents: ["claude", "codex"]`로 사용할 수 있습니다. Codex의 shell/exec_command 완료 이벤트는 `Bash`로 보고되므로 PostToolUse의 `^Bash$`만 수신합니다. 기존 read-only sandbox와 never approval 정책은 유지합니다. 모델 호출을 만드는 Stop 훅이나 신뢰 우회 플래그는 사용하지 않습니다.

설치한 HUB Python 환경에서 아래 명령으로 HUB 전용 훅 정의를 검토·등록한 다음 GUI의 Codex 도구 완료 수신 옵션을 켭니다. `<data-dir>`은 현재 HUB의 데이터 폴더입니다.

```text
python -m agent_hub.codex_boundary --data-dir <data-dir>
```

등록 명령은 native app-server hooks/list에서 HUB가 생성한 정확한 정의 하나를 선택하고 config/value/write로 그 해시의 신뢰를 등록합니다. 인증 파일은 읽거나 복사하지 않습니다. 전역 훅을 설치하지 않으며, 실행 시에만 CLI 설정으로 해당 정의를 전달합니다. 다른 훅을 일괄 승인하지 않습니다. 로컬 등록 기록은 boundary.py 내용, 훅 명령, Python 경로, native Codex home에 묶입니다. 코드·경로·계정 설정 폴더 변경 시 재등록합니다. 등록되지 않았거나 지문이 다르면 다음 과제 전달로 돌아갑니다. native에서 신뢰를 해제한 경우에도 수신 확인 없이 메시지를 소모하지 않습니다.

참고: https://learn.chatgpt.com/docs/hooks 및 https://learn.chatgpt.com/docs/config-schema.json. 초기 Claude 전용 검증 기록은 위에 보존하며 이 절이 Codex 추가 지원 범위를 설명합니다.

검증 (2026-09-16): Codex CLI 0.154.0의 실제 CLI 1회 실행에서 늦게 도착한 메시지 1건 전달·수신 ID 확인·일반 consult 1건 취소를 확인했습니다. 같은 격리 작업의 실행 지표도 호출 1회, 경계 수신 1건, 취소 1건, native 토큰 보고 1회로 일치했습니다. Python 회귀 테스트 77개 통과. 실제 Coral 채널에 테스트 메시지를 발송하지 않았습니다.


### 조건 원문 보존과 검토표 복구

사용자 최초 요청·추가 지침, 동료 질문을 이벤트 원문에서 재구성한 검토 목록으로 모든 과제에 전달합니다. R<event id>는 원문 메시지 단위 ID입니다. 자연어를 완벽하게 세부 조건으로 추출했다는 뜻이 아니며, 하나의 항목에 여러 조건이 있으면 검토자는 모두 확인해야 합니다. 사용자 항목과 동료 질문은 출처가 구분됩니다. 동료 질문은 검토·답변 대상이고 사용자 조건을 바꿀 권한은 없습니다. 이력 길이 제한으로 원문 항목이 빠지지 않습니다.

사용자 조건을 명시적으로 교체하려면 진행 중 같은 채널에 참여자를 멘션하고 `/replace R1 교체할 전체 조건`처럼 전송합니다. 해당 R1 메시지 전체를 대체하므로 유지할 조건도 적습니다. 이전 원문과 새 ID는 남습니다. 동료가 같은 명령을 보내도 교체되지 않습니다. 자연어로 상충하는 추가 지침을 보내면 임의로 이전 조건을 제거하지 않고 확인 대상으로 남깁니다.

검토 결과에는 모든 활성 항목의 requirement_checks(id, status=met/unmet/unclear, evidence)가 필요합니다. 근거 누락·항목 누락·중복은 승인되지 않습니다. unmet/unclear이면 OBJECT입니다. 항목이 추가되면 예전 목록으로 작성된 승인만으로 최종 합의를 통과하지 못합니다. 근거는 모델이 제출한 주장으로, 그 자체가 의미적 정확성의 증명은 아닙니다.

자동 검사는 제한된 구문만 지원합니다. 사용자 원문의 `Require key_fields ["tenant_id","user_id","revision"]`처럼 명시된 JSON 배열 포함 조건, 숫자 사칙연산 등식, python/py 코드 블록 및 명확한 수정 코드의 Python 문법을 검사합니다. 임의 코드를 실행하지 않으며, 일반 자연어 요구사항이나 모든 언어·코드 동작을 자동 검증하지 않습니다. 동료 주장을 자동으로 사용자 조건으로 승격하지 않습니다. 실패하면 쟁점으로 등록해 최대 V3 조율 안에서 수정·재검토하며 한도에서 보류합니다.

해시·결정 필드 또는 조건별 검토표 형식 오류는 과제당 한 번 재요청합니다. 원래 OBJECT의 decision/reply/issues를 바꾸면 복구 실패로 보류합니다. 교정은 승인 생성이나 의견 변경이 아니며 호출 한도에 포함됩니다. 최초 round/task/version 자체가 맞지 않거나 실행이 실패한 응답은 기존 차단을 유지합니다.

GUI에서 진행 중 고정된 조건, 검토 메시지의 조건별 근거, 결과의 조건 원문을 펼쳐볼 수 있습니다. 이전 기록에 근거가 없으면 소급해서 만들지 않습니다.

검증 (2026-09-16): 회귀 테스트 88개 통과. 실제 Claude opus / Codex gpt-6-astra에 revision 누락·Python 문법 오류 후보를 제시하고 Codex 최초 검토 해시의 한 글자를 테스트에서 제거했습니다. 원래 OBJECT/reply/issues를 유지한 1회 복구 후, 8회 CLI 호출·V2에서 전원 합의 및 자동 검사 실패 0건을 확인했습니다. 첫 실제 시도에서 발견한 실행 중 새 질문 경합은 실행 시작 목록 검증/최종 최신 목록 검증으로 수정하고 회귀 테스트로 고정했습니다. 테스트는 격리 수신함에서 수행했으며 실제 Coral 채널에는 게시하지 않았습니다.


## 간결한 토론 기본 흐름

각자 독립 의견(주장 1개, 근거 최대 2개, 우려 1개)을 준비한 뒤 동시에 공개합니다. 대표 한 명이 모든 의견의 실제 쟁점을 비교하고 필요한 상대에게만 질문합니다. 질문받은 에이전트만 추가 응답하며, 의무적인 전원 재발언 단계는 없습니다. 쟁점이 없으면 최종안을 작성하고 전원이 같은 최종안을 검토합니다. 3명 기준 추가 질문·반대·형식 재시도가 없는 기본 경로는 13회에서 8회 호출로 줄어듭니다.

검토 찬성은 ‘찬성’만 표시하고 조건별 검증 근거는 구조화된 결과에 보관합니다. 반대는 이유와 필요한 수정만 짧게 작성하며, 담당자 조사·수정 후 다시 전원 검토합니다. 독립 투표도 선택·핵심 근거·실제 우려만 짧게 작성합니다. 길이 목표는 프롬프트 지침이며, 요청한 코드나 중요한 근거를 잘라내지는 않습니다. 원문은 저장하고, 모델 입력에서 독립 의견의 중복과 이미 읽은 오래된 기록을 줄입니다.


## 작성자와 검토자 분리

새 토론부터 해당 버전 최종안의 실제 작성자는 투표에서 제외합니다. 다른 참여자 모두가 동일한 최종안에 승인해야 완료되며, 반대 시 담당 조사와 작성자의 수정 후 다시 검토합니다. 단독 참여는 자동 검사를 통과한 단독 작성 결과로 표시하고 상호 검증이나 합의를 주장하지 않습니다. 최종안 본문에는 합의 상태를 쓰지 않고 허브가 작성자·실제 검토 승인자를 붙입니다. 이전 토론의 투표 정책과 기록은 그대로 유지합니다. 3인 기본 경로는 독립 의견 3 + 쟁점 확인 1 + 통합 1 + 동료 검토 2 = 7회입니다.
