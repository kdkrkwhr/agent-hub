# 역할 분담 작업

상단 **작업 → 새 역할 작업**을 누르고 목표·결과물, 로컬 Git 저장소, 계획/구현/테스트·검토 담당자를 지정합니다. 검증 명령은 필요할 때만 입력합니다. 같은 에이전트를 여러 역할에 배정할 수 있으며 한 역할에 여러 명을 선택하면 표시된 순서로 실행합니다. 왼쪽 화살표로 순서를 바꿉니다. 기존 합의안이나 투표 결과의 **작업 준비** 버튼은 참고 내용을 작성창으로 가져올 뿐, 그 결과를 자동 실행하지 않습니다.

## 실행과 결과물

1. 깨끗한 Git 저장소의 HEAD를 별도 로컬 사본으로 복제합니다. 원본과 Git 메타데이터·객체를 공유하지 않고 origin 연결도 제거합니다. 미커밋 변경이 있으면 시작하지 않습니다.
2. 계획 담당자가 코드를 읽고 계획을 인계합니다. 구현 담당자는 사본의 실제 파일을 수정합니다. 여러 담당자는 병렬 편집하지 않고 지정 순서로 실행합니다.
3. 검증 명령이 있으면 Hub가 사본에서 실행하고 종료 코드·출력·파일 지문을 기록합니다. 검증 담당자는 그 기록과 파일을 확인합니다. 명령 통과만으로 완료하지 않고 지정된 검증 담당자 전원이 같은 파일에 대해 `done`을 제출해야 완료합니다.
4. 실패나 구체적인 수정 요청은 구현 담당자에게 돌아갑니다. 최초 시도 외 수정 재시도를 0~3회 지정할 수 있습니다. 인프라·권한·형식 오류는 무작정 재시도하지 않고 보류합니다.
5. 완료 시 변경 패치, 변경 파일 ZIP, 보고서를 다운로드할 수 있습니다. ZIP에는 변경·추가된 파일이 들어가며 삭제 내역과 기준 커밋은 manifest와 패치에 담깁니다. 원본에 자동 적용·커밋·푸시하지 않습니다. 적용 전 원본에서 `git apply --check changes.patch` 등으로 별도 확인하세요.

완료는 지정된 담당자의 결과물 검토가 끝났다는 뜻입니다. 검증 명령을 입력한 경우에는 해당 명령도 통과해야 합니다. 명령을 생략한 작업은 테스트 미실행으로 표시합니다. 요구사항의 완전성이나 모든 오류 제거를 보장하지 않습니다. 작업별 사본은 결과 확인을 위해 자동 삭제하지 않으므로 데이터 폴더의 workspaces/runs/artifacts가 누적됩니다.

## 통신과 충돌 방지

역할별 인계·질문·답변을 기존 대화방에 표시합니다. 질문은 배정된 다른 에이전트에게만 최대 2개 전송할 수 있습니다. Hub가 읽기 전용 답변 단계를 실행한 뒤 요청자의 단계를 한 번 다시 실행합니다. 기존 편집을 보존하며 반복 질문은 보류합니다. 사무실에서는 계획·질문은 회의 공간, 구현은 작업석, 검증은 리뷰룸으로 표시합니다.

한 채널에서 토론·투표·역할 작업을 동시에 시작하지 않습니다. 동일 Hub DB에서 같은 프로젝트(공통 Git 디렉터리 기준)의 역할 작업을 중복 실행하지 않습니다. 다른 Hub 인스턴스나 외부 편집기를 제어하는 분산 잠금은 아닙니다. 파일 지문으로 검증 대상 변경을 확인하고, 검증 명령이나 읽기 전용 단계가 소스를 변경하면 보류합니다.

역할 작업 중 일반 메시지는 대화 기록으로만 남습니다. 실행 중 지문·배정을 바꾸거나 0-turn 메시지를 주입하지 않습니다. 요구사항 변경은 중지 후 새 작업으로 요청하세요. 기존 토론의 0-turn 설정은 유지됩니다. Coral에는 최종 상태만 멘션 없이 전달하고 내부 단계·질문 기록의 원본은 Hub DB에 보존합니다.

## 지원 범위와 권한

- 첫 버전은 커밋된 로컬 Git 저장소만 지원합니다. 서브모듈과 심볼릭 링크는 지원하지 않습니다. 추적 파일과 Git에서 무시하지 않는 새 파일을 검사·내보냅니다. 파일 2만 개, 파일당 32MB, 합계 256MB 한도가 있습니다.
- CLI 호출은 최대 10분, 검증 명령은 최대 5분, 작업 전체는 2시간과 30단계 실행 한도입니다. 준비·질문·재실행도 단계 수에 포함됩니다. 취소·재시작 시 작성된 사본은 남고, 실행 중이던 쓰기 작업을 자동 재실행하지 않습니다.
- 검증 명령은 사용자가 지정한 로컬 프로그램을 실행합니다. `&&`, 파이프 등의 셸 조합은 지원하지 않습니다. Windows npm은 발견한 npm-cli.js를 node로 실행합니다. 의존성 설치를 자동 수행하지 않으며 원본의 무시된 node_modules/가상환경도 복사하지 않습니다. 필요한 의존성이 있는 Python 실행 파일 등을 검증 명령에 지정하세요.
- 구현 단계에만 쓰기 기능을 부여합니다. Claude는 Read/Glob/Grep/Edit/Write, Codex는 workspace-write를 사용합니다. 계획·검증·질문 단계는 기존 읽기 모드입니다. 테스트 명령은 모델 대신 Hub가 실행합니다.
- Windows Cursor CLI는 OS 샌드박스를 지원하지 않아 기본 권한 설정을 사용합니다. 다른 플랫폼은 sandbox enabled를 요청합니다. `--force`, 무제한 권한, 권한 우회 플래그를 사용하거나 사용자 전역 설정을 변경하지 않습니다. 기본 권한에서 쓰기가 거부되면 보류됩니다. [Cursor 권한 문서](https://prod.cursor.com/docs/cli/reference/permissions)를 참고하세요.
- 사본 분리는 원본 자동 덮어쓰기와 작업 간 충돌을 피하기 위한 것입니다. 모든 CLI와 사용자 검증 명령에 대한 OS 수준의 보안 격리나 원본 접근 차단을 보장하지 않습니다. 실행 권한은 각 CLI와 운영체제 정책에 따릅니다.

## 검증

실제 Claude 계획 → Codex 구현 → Cursor 검토가 모델 호출 3회, 약 158초에 완료되었습니다. 실제 unittest가 통과하고 변경 패치가 생성됐으며 원본의 파일 지문은 그대로였습니다. 기존 Coral 채널에 테스트 메시지를 게시하지 않았습니다. 브라우저에서는 역할 중복 배정·순서 변경·초안 보존·결과물 다운로드와 1320/480px 화면을 확인했습니다. 별도 기록은 docs/benchmarks/2026-09-16-pipeline 아래에 있습니다.

최종 Python 회귀 테스트 113개와 사무실 테스트 7개가 통과했습니다. 구현 역할을 바꾼 추가 테스트에서도 Claude(23초), Cursor(77.3초)가 별도 사본에 실제 파일을 작성했습니다. Windows Cursor는 처음 강제한 OS 샌드박스 옵션이 지원되지 않아 실패했고, 권한 우회 없이 기본 권한 검사로 재검증했습니다.


## 작업 메뉴와 검증 명령 추천

상단 **작업** 탭에서 채널별 역할 작업을 생성하고 진행 단계, 인계 기록, 검증 로그와 결과물을 확인합니다. 기존 개별 자동 실행 목록은 이 화면에서 제거했으며 대화·사무실 기능과 실행 기록은 유지합니다.

작업 생성 시 **프로젝트에서 찾기**는 package.json의 테스트 스크립트, pytest 설정, 직접 하위 테스트 파일의 pytest/unittest import를 읽어 후보를 표시합니다. 후보를 선택하거나 직접 입력할 수 있습니다. 조회는 프로젝트 코드를 실행하거나 패키지를 설치하지 않습니다. 설정을 찾지 못하면 직접 입력 안내를 표시합니다. Python 후보는 Hub를 실행한 Python 경로를 사용하며, 의존성 설치 여부나 테스트의 충분성은 보장하지 않습니다. 하위 패키지별 모노레포 설정은 자동 탐색하지 않습니다.


검증 명령은 선택 사항입니다. 빈칸이면 명령을 실행하지 않고 검토 담당자가 동일한 결과물을 확인합니다. 이 경우 결과와 보고서에 테스트 미실행을 기록하며 테스트 통과로 표시하지 않습니다. 검토자의 수정 요청과 파일 변경 감지는 그대로 적용됩니다.


## 작업 후 대화

같은 채널에서 새 토론을 시작하면 최근 종료된 역할 작업(완료·보류·취소)의 목표, 상태, 테스트 여부, 최근 인계 기록, 변경 파일 목록과 사본·보고서 경로를 참고 자료로 고정해서 전달합니다. 다른 채널의 작업은 포함하지 않습니다. 과거 작업 카드의 **이 작업에 대해 대화하기**로 특정 작업 ID를 질문에 넣을 수도 있습니다. 긴 기록은 일부만 전달하며 필요하면 사본/보고서를 읽어 확인합니다. 이전 작업 목표를 새 요청의 의무로 취급하지 않으며 실제 원본 적용이나 테스트 통과를 추정하지 않습니다. 진행 중 작업에 대한 메시지 전달 정책은 유지됩니다.


## 후속 작업과 사무실 개별 실행

완료된 작업 카드의 **후속 작업 요청**에서 기존 사본을 선택해 문서화·추가 수정을 진행합니다. 새 사본을 생성하지 않으며 원본 저장소가 아니라 기존 작업 사본을 이어 씁니다. 이전 결과물 다운로드는 보존하고, 후속 패치·ZIP은 최초 기준 커밋 대비 누적 변경을 담습니다. 각 실행의 요청·인계·검토 기록은 별도로 남습니다.

**사무실 → 캐릭터 선택 → 이 에이전트에게 작업 요청**에서 담당자·대상 작업·지시를 확인하고 실행합니다. 기존 완료 작업이 없으면 새 사본을 만들 수 있습니다.

- 역할 분담: 기존 계획 → 구현 → 검토 단계.
- 개별 작업: 선택한 한 명이 구현 → 자체 검토. 독립 교차 검토는 아닙니다.
- 개별 질문: 한 번의 읽기 전용 질의. 파일 수정·테스트 명령 없이 답합니다.

같은 작업 공간의 가장 최근 완료 작업만 이어 쓸 수 있습니다. 다른 채널·연결의 작업, 외부 수정된 사본, 실행 중 작업은 거부합니다. 시작 전 기존 파일 지문도 다시 확인합니다. 보류·취소된 후속 작업에서 자동 복구하거나 과거 상태로 되돌리지는 않습니다. 동일 프로젝트에는 한 작업만 실행합니다.

후속 작업 후 과거 사본 경로는 최신 내용이므로, 과거 결과는 그 작업의 보존된 패치와 보고서를 기준으로 확인해야 합니다. 후속 대화에도 이 구분을 전달합니다. 에이전트 실행 자체는 커밋·push·배포하지 않습니다. 완료 후 아래 원본 반영 화면에서 Git 작업을 별도로 선택할 수 있습니다.


## 원본 반영 · 커밋 · push

결과물이 있는 완료 작업에서 **원본 반영 · 커밋 · push**를 누릅니다. 대상 저장소, 현재 브랜치, origin의 push 주소, 파일 목록, diff를 확인한 뒤 실행 범위를 선택합니다. 기본값은 **원본 반영 · 스테이징만**입니다. 커밋은 직접 입력한 메시지를 사용하며 push는 명시적으로 선택한 경우에만 수행합니다.

- 원본 HEAD가 작업 시작 기준과 같고, 미커밋·미추적 파일이 없는 상태에서만 처음 반영합니다. 기존 변경을 자동 stash·병합·삭제하지 않습니다.
- 적용할 패치 전체를 `git apply --check --index`로 확인합니다. 반영 후 인덱스 트리가 미리 계산한 결과와 같아야 커밋합니다.
- 같은 프로젝트의 Hub 작업이 실행 중이면 반영하지 않습니다. 외부 편집기나 다른 Git 프로세스와의 분산 잠금은 없으므로 해당 작업을 중지하고 진행하세요.
- 현재 브랜치만 대상으로 합니다. push는 origin에 해당 브랜치가 이미 있고 원격 끝 커밋이 작업 기준 또는 이번 커밋과 일치할 때만 허용합니다. 다른 미푸시 커밋이나 원격 변경을 자동 포함하지 않습니다. 강제 push·새 브랜치 생성은 지원하지 않습니다.
- 미리보기는 10분간 유효합니다. 실행 직전에 패치·브랜치·원격·원본 상태를 다시 검사합니다. diff는 80KB까지 표시하며 큰 패치는 다운로드해 확인하세요. 반영 가능한 패치는 16MB 이하입니다.
- 적용·커밋·push 상태는 따로 보관합니다. 반영 후 창을 다시 열어 커밋하거나, 커밋 후 push할 수 있습니다. 실패 시 완료된 단계는 보존합니다. 적용/커밋 도중 프로세스가 중단됐다면 수동 상태 확인이 필요하며 자동 재실행하지 않습니다.
- 커밋·push는 원본 저장소의 Git 훅을 사용합니다. 훅 실패나 시간 제한 초과 시 해당 단계가 중단될 수 있습니다. Git의 사용자 이름·이메일·서명·원격 인증도 사용자의 환경 설정을 사용합니다.

원본에 다른 커밋이 생기면 기존 기준의 누적 패치를 다시 반영하지 않습니다. 원본에 반영한 뒤 추가 수정·게시를 이어가려면 최신 원본에서 새 작업을 시작하세요. 테스트 생략 상태는 게시하더라도 그대로 표시합니다.


## 작업 유형

작업 요청 창에서 자동·조사/분석·기능 개발·수정/개선·문서 정리를 선택합니다. 자동은 별도 모델 호출 없이 실행 방식과 요청의 키워드로 분류합니다(읽기 전용 → 조사, 문서 키워드 → 문서, 수정/성능 키워드 → 개선, 나머지 → 개발). 복합 요청은 직접 지정할 수 있습니다. 유형은 지침과 완료 기준에 반영하며 결과 카드에도 표시합니다. 조사·분석을 선택하면 읽기 전용으로 전환합니다. 기존 작업은 새 유형을 소급 지정하지 않습니다. 후속 작업의 유형은 새 요청에서 정합니다.
