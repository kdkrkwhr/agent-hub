# Agent Hub Radio — Anna 첫 출시·심사 준비 계획

작성일: 2026-10-22

검토 기준: `release-anna` / `c806527` / Anna 앱 버전 `0.6.0`
목적: 현재 구현을 다듬어 실제 사용 검증과 Marketplace 심사 제출까지 진행하기 위한 작업 범위·순서·완료 조건 정리

사용자 확정 사항(2026-10-22): **첫 심사 요청 버전은 1.0.0으로 한다.** 0.x는 개발·테스트 단계로 유지하고 심사를 제출하지 않는다. 1.0.0은 아래 검증과 소개 자료 준비를 마친 뒤 생성한다. 제품 가치 검토 뒤 사용자가 진행을 승인하여 0.7.0 테스트 번들 작업을 시작했다.

업데이트: 첫 사용 장면을 **개인 개발자의 다음 출시 기능 우선순위**로 좁혔다. 빠른 검토·결정 요약과 P0 저장/빈 응답 문제를 먼저 구현했다. 아래 현재 상태 표는 최초 조사 당시 기준이며, 이후 결과는 [0.7.0 검증](VALIDATION_070.md)과 [최신 인수인계](HANDOFF.md)를 따른다.

## 1. 추천하는 첫 출시 방향

**“하나의 고민을 분석가·비판자·정리자의 관점으로 검토하고, 선택지를 비교해 결정을 정리하는 AI 회의실.”**

첫 출시는 이미 구현된 **토론·독립 투표·기록**에 집중한다. 문서 파이프라인은 별도 후속 업데이트로 분리하는 것을 기본안으로 삼는다. 이는 아직 확정되지 않은 범위 제안이며, 문서 작성까지 첫 출시에 포함하기로 결정하면 일정과 검증 범위를 다시 산정한다.

추천 사용 장면:

- 개인 개발자: 이번 주에 먼저 구현할 기능, 출시 범위, 홍보 문구 검토
- 기획자: 제품 아이디어의 장점·위험·빠진 조건 비교
- 작은 팀: 2~6개 선택지를 놓고 각 역할의 선택과 근거 확인

토론의 가치는 AI 메시지가 많이 나오는 것보다 **왜 이 결론에 도달했는지, 어떤 반론이 남았는지 쉽게 확인하는 것**에 둔다. 사무실 지도는 진행 상황을 보여주는 보조 화면으로 유지한다.

### 제품 설명에서 구분할 것

- Anna 앱의 세 역할은 LLM 프롬프트로 구분된 역할이다. 실제 Claude Code·Codex CLI·Cursor 프로세스를 실행하는 로컬 Agent Hub와 다르다.
- 서로 다른 모델을 반드시 사용하는 것은 아니다. 모델 설정은 선호 조건이며, 실제 사용 모델을 응답에 표시한다.
- 독립 투표는 다른 역할의 투표 내용을 프롬프트로 전달하지 않는 방식이다. 서로 독립적인 인간 전문가나 통계적으로 독립된 모델의 판단을 보장하는 표현은 쓰지 않는다.
- 코드를 실행하거나 사용자 파일을 직접 고치는 기능은 Anna 첫 출시 범위에 없다.
- AI 결과는 검토할 제안이다. 합의가 생겼다고 사실 확인이나 정확성 검증을 마친 것으로 표현하지 않는다.

## 3. 작업 순서와 완료 조건

### 0단계 — 출시 범위·현재 배포 상태 확정

- Developer Console에서 앱 ID, 설치 draft, 최신 버전과 제출 여부를 읽어서 기존 기록과 대조한다.
- 기존 사용자 채널·기록은 유지한다. 데이터 형식을 바꿔야 할 때만 호환 읽기·마이그레이션을 설계한다.
- 현재 저장소의 미추적 `.claude/`, `skills-lock.json`은 이번 검토 전에 존재한 사용자 파일이므로 임의로 정리하거나 커밋하지 않는다.
- 첫 출시 기능은 토론·투표·기록·사무실로 고정한다. 채팅 파일 첨부, 로컬 CLI 연결, 자동 코드 수정, 신규 서버는 이번 범위에서 제외한다.

**완료 조건:** 실제 배포 기준과 변경 범위가 기록되고, 소개에 넣을 기능마다 동작하는 화면이 있다.

### 1단계 — AI 사용과 저장 실패 처리 보강

우선 수정 파일: `bundle/runner.mjs`, `bundle/ai.mjs`, `bundle/store.mjs`, `bundle/timeline-view.mjs`, `bundle/i18n.mjs` 및 관련 테스트.

1. **저장 실패 시 실행 일시 중지**
   - 다음 AI 요청 전 필요한 실행 상태가 저장됐는지 확인한다.
   - 응답을 받았지만 저장에 실패하면 화면에 결과를 유지하고 `저장 다시 시도`를 제공한다.
   - 저장 재시도는 AI를 다시 부르지 않는다. 저장이 복구된 뒤에만 남은 단계를 이어갈 수 있다.
   - 저장 안 됨, 응답 실패, 사용자 중단, 정상 완료를 구분한다. 브라우저를 닫으면 메모리의 미저장 응답이 유실될 수 있음을 해당 상태에서 안내하고 복사할 수 있게 한다.
2. **빈 응답·중간 종료 구분**
   - 공백만 있는 응답을 성공 처리하지 않는다.
   - SDK가 제공하는 경우 종료 사유·출력 제한·필터링 정보를 확인한다. 부분 결과를 완성된 답변처럼 표시하지 않는다.
   - 투표 응답은 유효한 선택/기권과 근거를 검증하고, 실패한 역할을 처리하기 전 공개하지 않는다.
3. **중단·재개와 중복 사용 방지**
   - 이미 응답을 받고 저장한 단계는 다시 실행하지 않는다.
   - 창 종료·타임아웃 후 서버 처리 여부를 모르는 요청은 상태를 명확히 표시한다. API가 중복 요청 방지 키를 지원하는지 확인하고, 지원하지 않으면 정확히 한 번 실행된다고 보장하지 않는다.
   - 사용자가 중단하면 후속 요청을 막는다. 이미 시작된 서버 생성까지 취소되는지는 별도로 검증한다.
4. **실제 권한·저장 제한 확인**
   - `llm.complete` 권한과 `llm.stream` 가용성을 실제 앱에서 대조한다. 지원되지 않는 스트리밍을 반복 시도하는 구조는 정리한다.
   - 공식 제한에 맞춰 UTF-8 기준 레코드 크기·누적 인덱스를 검증한다. 제한 근처에서는 설명과 복구 방법을 제공하고 기록을 조용히 잘라내거나 삭제하지 않는다.
   - 앱의 `single_instance` 설정만으로 여러 기기 실행까지 막힌다고 가정하지 않는다. 다중 창·기기 충돌과 저장 API의 조건부 갱신 지원 여부를 확인해 필요한 최소 대응을 정한다.

**완료 조건:** 지속 저장 실패·빈 응답 재현 테스트가 수정 후 통과한다. 받은 응답의 저장 재시도에서 추가 AI 호출은 0회이고, 저장 장애 중 후속 AI 호출이 발생하지 않는다. 기존 데이터 읽기와 정상 토론·투표 테스트도 통과한다.

### 2단계 — 결과를 읽고 결정하기 쉬운 화면

1. **빠른 검토 / 심층 토론 선택**
   - 새 빠른 검토: 역할별 의견 N회 + 정리 1회. 3역할이면 **4회** 호출.
   - 기존 심층 토론: 의견 N회 + 반박 N회 + 최종안 1회 + 동료 검토 N−1회. 3역할이면 **9회** 호출, 2역할이면 6회.
   - 독립 투표는 참여 역할 수만큼 호출한다. 3역할이면 3회.
   - 기본값은 빠른 검토를 제안한다. 기존 저장 기록은 원래 실행 방식으로 계속 읽고 재개한다.
   - 호출 횟수는 토큰 사용량이나 청구액과 같지 않다. 정확한 가격을 임의로 추정하지 않는다.
2. **최종 결과를 별도 영역에 표시**
   - 추천안, 주요 이유, 남은 반론, 다음 행동을 읽기 쉽게 묶는다.
   - 원래 최종 정리 요청에 해당 형식을 요구하고, 화면 표시를 위해 별도 AI 요청을 추가하지 않는다.
   - 심층 토론의 최종안 이후 동료 검토에서 제기한 이견은 결과와 함께 보여준다. 검토가 끝났다는 이유만으로 전원 합의라고 표시하지 않는다.
   - 역할별 전체 발언은 펼쳐서 읽고, 결과만 복사하거나 전체 기록을 내보낼 수 있게 한다.
3. **투표의 판단 근거 강조**
   - 결과 공개 후 선택지별 득표·기권·실패/건너뜀 수를 분리한다.
   - 각 역할이 왜 선택했는지와 우려 사항을 함께 보여준다.
   - 완료 전에는 역할의 선택을 채팅·지도·복사/내보내기에서 노출하지 않는 현재 원칙을 유지한다.

**완료 조건:** 완료된 실행에서 추천안과 반론을 쉽게 찾을 수 있고, 원문으로 이동할 수 있다. 예상 호출 수와 실제 요청 수가 일치하며, 화면 전환·복사·기록 열람에서는 AI를 호출하지 않는다.

### 3단계 — 첫 사용과 작은 화면 다듬기

- 처음 화면에 기능을 설명하는 짧은 문장과 바로 입력 가능한 예시 3개를 제공한다. 예: 출시할 기능 우선순위, 제품 아이디어 위험 점검, 홍보 문구 비교.
- `주제 입력 → 방식 선택 → 결과 확인` 흐름을 먼저 보여주고 세부 모델 설정은 필요할 때 연다.
- 이전 대화가 자동으로 문맥에 포함되지 않는 현재 방식을 안내한다. 연속 대화 기능을 암묵적으로 약속하지 않는다.
- 실행 전에 예상 호출 횟수와 사용자 Anna AI 사용량을 쓴다는 점을 안내한다. 할당량 부족·모델 미사용 가능 상태에서 다음 행동을 알려준다.
- 사무실은 역할의 현재 단계와 상태를 읽을 수 있게 정돈한다. 새 그래픽 시스템이나 게임 수준의 사무실 개편은 이번 출시의 선행 조건으로 두지 않는다.
- 360px 화면과 실제 Anna 소형 창에서 입력창, 결과, 모달, 중단·재개 버튼의 잘림과 가로 넘침을 확인한다.
- 한국어·영어에서 새 상태 안내와 버튼 명칭을 함께 적용하고 키보드 포커스·대비도 점검한다.

**완료 조건:** 새 사용자에게 개발 설명 없이 예시 하나를 완료할 경로가 보인다. 지원하는 창 크기에서 핵심 조작이 가려지지 않는다. 반응형 점검만으로 Anna의 모바일 앱 지원을 선언하지 않는다.

### 4단계 — 설치된 Anna에서 실제 AI 검증

코드·모의 테스트가 통과한 번들을 소유자 테스트 앱에 설치한 뒤 수행한다. 이 단계부터 실제 Anna AI 사용량이 발생하므로 사용할 계정의 잔여량을 먼저 확인하고 검증 횟수를 정한다.

| 시나리오 | 확인할 결과 |
|---|---|
| 빠른 검토 1건 | 역할별 관점이 구분되고 입력한 고민에 답하는 최종안이 나옴 |
| 심층 토론 1건 | 반박이 앞선 의견을 참조하고 마지막 검토의 이견이 결과에 보임 |
| 독립 투표 1건 | 선택이 끝나기 전 비공개, 집계·기권·근거가 일치 |
| 모델 선호 설정 | 실제 모델 표시, 선호와 다른 배정 시 안내, 알려지지 않은 모델은 추측하지 않음 |
| 중단·재접속·재개 | 저장된 완료 단계는 유지, 불확실한 진행 상태 안내, 무조건 자동 재실행하지 않음 |
| 할당량·권한·연결 문제 | 오류 원인에 맞는 다음 행동 제시, 사용자의 선택 없는 유료 재시도 없음 |
| 저장 장애 복구 | 이미 받은 답변 저장만 재시도, 후속 AI 요청 중단 |
| 긴 한국어/영어 입력·기록 | 잘림·크기 초과·이전 기록 로딩을 확인하고 데이터 보존 |
| Markdown 복사·다운로드 | 실제 Anna 환경에서 복사 및 `.md` 파일 저장 가능 |
| 별도 테스트 계정 | 새 사용자 첫 화면과 계정 간 채널·설정 격리 확인 |
| 한국어·영어, 실제 창 크기 | 버튼·상태 안내·사무실·결과 표시 확인 |

정상 AI 흐름의 기본 검증량은 기존 기능만이면 토론 9 + 투표 3 = **12회**다. 빠른 검토까지 구현하면 빠른 검토 4 + 심층 토론 9 + 투표 3 = **16회**가 기본이다. 중단·재시도·추가 언어 검증은 별도이며, 무한 반복 테스트를 하지 않는다. 할당량을 소진시켜 오류를 만들지 말고 실패 분기는 우선 모의 테스트로 검증한다. 실제 환경에서 재현하지 못한 항목은 미확인으로 남긴다.

**완료 조건:** 설치한 revision/번들, 실제 사용 모델, 실행 결과, 지원 환경과 남은 제한을 기록한다. 모의 화면과 실제 서비스 결과를 구분한다.

### 5단계 — 소개 자료와 심사 제출

1. **Anna 전용 사용자 안내**
   - `anna/README.md`를 만들고 루트 README에서 연결한다. 기존 로컬 Agent Hub 설명을 지우지 않고 실행 방식의 차이를 명시한다.
   - 설치·첫 토론·투표·모델 설정·AI 사용량·실패 복구·기록 삭제/내보내기·문의 방법을 짧게 안내한다.
   - 입력과 결과가 Anna AI 및 앱 저장소를 통해 처리된다는 실제 데이터 흐름을 설명한다. 현재 확인할 수 없는 보관 기간·플랫폼 학습 정책 등을 임의로 단정하지 않는다.
2. **스토어 메타데이터**
   - `app.json` 및 manifest 안내를 실제 기능에 맞게 수정한다. 미구현 문서 파이프라인 표현은 제거한다.
   - 권한 목록, 외부 통신, 지원 환경을 최종 구현과 대조한다. 현재 구조에는 Executa가 없으므로 패키지 작업을 새로 만들 필요는 없다.
   - 안내 페이지·문의 링크가 공개 상태에서 열리는지 확인한다.
3. **실제 화면 캡처 3~4장**
   - 첫 화면과 예시 입력, 토론 결과·반론, 공개된 투표 결과, 사무실 진행 화면.
   - 최종 테스트 앱에서 직접 얻은 읽을 수 있는 결과를 쓴다. 모의 `응답 1` 같은 테스트 데이터와 개인정보는 소개 이미지에 쓰지 않는다.
4. **심사자 재현 순서**
   - 새 채널 → 예시 주제로 빠른 검토 → 결과·실제 모델 확인 → 3개 선택지 투표 → 결과 확인 → Markdown 저장.
   - 3역할 기준 빠른 검토 4 + 투표 3 = 7회 호출을 안내한다. 별도 CLI·서버·개발 환경이 필요 없다는 점을 설명한다.
   - AI 사용량 소진 시 정상 안내가 나온다는 점과 알려진 제한을 심사 메모에 적는다.
5. **검증된 번들로 후보 생성·제출**
   - 단위·브라우저 테스트 및 strict validation → Git 커밋/푸시 → 테스트 draft 업로드·설치 → 실제 흐름 확인 순서로 진행한다.
   - 작업 중 버전을 계속 올리지 않고 검증된 번들에 첫 심사용 버전 `1.0.0`을 부여한다. 생성 전 Console에서 사용 여부를 확인한다. 충돌 시 기존 버전을 덮어쓰거나 임의로 다른 심사 버전을 제출하지 않고 버전 계획을 조정한다.
   - 후보 번들과 테스트한 번들이 일치하는지 확인한 후 설명·스크린샷·심사 메모와 함께 제출한다.
   - 제출 버전, 날짜, Console 상태, 검증 결과를 `HANDOFF.md`와 새 릴리스 노트에 기록한다. 검토 결과가 오면 지적 사항을 기준으로 수정·재검증한다.

**완료 조건:** 핵심 기능 미완성이나 알려진 P0 문제가 없고, 스토어 설명·화면·제출 번들이 일치한다. 제출 완료는 Console 상태를 확인한 뒤 기록한다.

Anna 공식 안내는 핵심 기능, 소개와 실제 경험의 일치, 명확한 스토어 자료, 사용 흐름, 권한·실행 안전성을 검토한다고 설명한다. 제출·재제출은 각각 5영업일 내 처리 기준이며 접수량에 따라 피드백이 늦어질 수 있으므로 일정에 여유를 둔다. [공식 심사 절차 안내](https://forum.anna.partners/t/app-review-timeline-process/318) — 2026-10-22 확인.
